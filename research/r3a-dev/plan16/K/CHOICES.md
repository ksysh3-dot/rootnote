## 2. Hit detector (M3, the exact 16.10.1 text)
* Input: `DATA.audio(key)` 48 kHz, mono = (L+R)/2 (audio is stereo float32).  Two 4th-order Butterworth band-passes (40-200 Hz, 1-8 kHz; `scipy.signal.butter(2, band, 'bandpass', output='sos')` gives order-4 band-pass sections), causal `sosfilt`, 128-sample non-overlapping blocks, log energy 10 log10(sum x^2 + 1e-12) (floor 1e-12 per block, about -120 dB, only to avoid log(0)).
* Trigger at block b: both bands' log energy > median of their previous 19 blocks + thr_db (grid axis; literal 9).  t_d = b*128/48000 (block start); window = [t_d, t_d + W] (W grid axis; literal 60 ms); no re-trigger while b*128 < t_d + 60 ms (refractory 60 ms from the trigger, independent of W: the refractory is 60 ms for every W).  Blocks 0-18 cannot trigger (need 19 blocks).
* Reported only (not judged): recall of MIDI hits in H (a hit d counts if some t_d lies within +-40 ms), false-window share (windows with no H hit within +-40 ms of t_d), number of bass-note starts lying inside a false window.  H = GM drum pitches 35, 36, 38, 40, 41, 43, 45, 47, 48, 50 (kicks, snares, toms; no hi-hat/cymbal).  Drum MIDI is read with the same drum-stem rule as `common16.ref` (copied into kcommon, per-pitch onsets).
* The detector window and the voice axis are compared on the same axis (audio time = layer time); STREAM_DELAY is not used (M6).

## 3. Voice events and interventions (M5; ramps; M4 rebirth)
Event unit = (voice run, window).  For a window [t_d, t_e = t_d + W] and a voice run with hop layer times T_h = tc[h] + LAG:
* Window hops = hops with t_d <= T_h < t_e.  Alive window hops = window hops with amp > 0.  No alive window hop -> no event.
* pre-hop = the hop of the run just before the first window hop; amp_pre = amp there (0 if no such hop); runmax = max amp of the run up to the pre-hop (causal).  If amp_pre = 0 or amp_pre < 0.01 runmax (the 1 % of M5, read relative to the voice's own causal running maximum because a song-wide maximum is not causal) the event is a BIRTH (new voice); else a RISE.
* BIRTH gain g0 = 10^(gain_db/20) (grid axis; literal -12 dB = 0.251) multiplies amp, from the first alive window hop.  RISE: amp is limited to cap = amp_pre 10^(3/20); gain at a hop = min(1, cap/amp); only hops with amp > cap are affected; no affected hop -> no event.
* Transition into the restriction: 5 ms linear ramp of the gain (knot at T_first - 5 ms with gain 1, knot at T_first).  Gains are linear ramps in the amplitude domain, applied per render sample (3 kHz) on top of the hop-linear amp interpolation (`np.interp`), not at hop resolution.
* Confirmation (section 4) at hop T_c: gain ramps linearly to 1 within 10 ms (BIRTH: from g0; RISE: from the current cap gain).  A confirmed voice is not re-restricted in that window.
* Not confirmed at t_e: 15 ms linear fade of the gain to 0 starting at t_e (BIRTH: the voice is released; RISE: the voice is not released, its amplitude is pulled to amp_pre: gain -> min(1, amp_pre/amp), a 15 ms fade from the capped value, then held at min(1, amp_pre/amp) until t_e + 40 ms).
* Return after release (M4 "rebirth ban" model) -- primary reading B: BIRTH stays at gain 0 until t_e + 40 ms (the engine rule "same trackId may not make a new voice until window end + 40 ms"), then ramps to 1 within 10 ms (the track still exists, the engine would re-create the voice); RISE: the amp_pre hold ends at t_e + 40 ms, ramp to 1 within 10 ms.  Sensitivity reading A: the voice stays released (gain 0 / amp_pre hold) until the end of its run, reported for the selected setting and for stage 0.  LIMITATION (written here per M4): the offline sim treats the release interval as gain 0 and cannot show a re-birth/RERISE inside the engine; the C++ pre-registration must contain the rebirth-ban rule.
* Multiple events on one voice multiply their gains.

## 4. Confirmation evidence K1-K3 (B2, M1)
Evaluated at every window hop h of the event from the first alive window hop (BIRTH) or the first window hop (RISE) to t_e; only data up to hop h (voice time) is read; the index of every stream/trace sample read is logged (leak log, section 8).
* K1 pitch stable: tracker f (trace field 5, `ftr`) over the hops h-3..h (T_h - 16 ms .. T_h; 4 hops = 16 ms, 5 hops would be 21.3 ms) has (max-min) <= 30 cent.  All four hops must belong to the run (state > 0); otherwise K1 = false (no history -> false, B2 rule).
* K2 harmonic structure: peaks list rebuilt with the engine recipe of `diag16/q4.py src_peaks` from the `det` stream (vectorised re-implementation in kcommon, checked equal to the q4 loop on a sample of hops), frame end at the hop's stream index.  True iff a peak lies within 30 cent of the tracker f (its `rel` = r1; if several the nearest) AND a peak within 30 cent of 2f or of 3f has rel >= r1 - 20 dB.  No peak at f -> false.  Which index convention (det[j] vs det[j-191]) matches the engine `prominent` flag is decided by the agreement rate on a sample of voice-hops; the better one is used and both agreement rates are reported FIRST.  Control (0a): same test with f x 1.06.
* K3 slow decay: over the last 20 hops of the run (<= 107 ms) take the hop of the maximum amp (first one if tied); dt = T_h - T_peak; K3 true iff dt >= 15 ms and 20 log10(amp_peak/amp_h)/dt <= 120 dB/s (grid-fixed 120; amp_h = 0 -> false).  The decay-rate statistic is also reported as a distribution in 0a.
* Confirmation = 2-of-3 true at two consecutive hops inside the window (hops h-1 and h both in the evaluated range); confirmation time T_c = T_h of the second one.  Once confirmed, final for that window (no revert).
* 0a also reports "any hop 2-of-3" and "2-of-3 at the last window hop" next to the consecutive-hop confirmation rate.

## 5. Stage 0 (dev tracks, core v1.5 trace; literal setting thr 9 dB, W 60 ms, -12 dB, K3 120)
* Populations (event unit): (A) events of SILENCE-class voices (cls = 2) whose voice has >= 50 % of its sa-wrong energy (a^2 proxy) tagged cause 2 (drum); (B) events of MATCHED-class voices (cls = 0: occupancy winner exists and `compat`, i.e. compatible with the bass MIDI) that are births/rises in a window.  Count-based rates are the pre-registered primary; the energy-weighted rate of A (weight = cause-2 a^2) is printed beside.  Information: group C = other silence voices in windows.  Stop conditions as in 16.10.1: A (consecutive-hop) <= 40 %, B >= 80 %, K2 control <= 25 % (judged separately for A and B, both must hold).
* K1/K2/K3 true fractions: hop level (pooled over the event hops) and event level ("true at some hop of the window"), for A and B, per song and pooled.  K3 decay-rate distribution (deciles) for A and B.
* 0b: R_det = cause-2 energy in the render samples lying inside a detector window / all cause-2 energy.  R_max = reduction (1 - E_oracle/E_core, pooled and per song, with and without T25) of the cause-2 energy of the ORACLE: every window birth gets gain_db, every rise cap +3 dB, never confirmed, 15 ms fade to release at t_e, reading B return.  Additional bracket (reported): hard oracle with RISE voices also at -12 dB multiplicatively.  Stop if R_max (pooled sum) < 55 %.
* 0c: same oracle with a confirmation delay L = 20 and 35 ms (T_c = event start time + L, no evidence), co-hit attack (section 7) change in dB per song and pooled (also L = infinity = the 0b oracle).  Stop if worse than -2 dB (pooled or per eligible song).
* Hop agreement of K2 emulation with the engine `prominent`: reported first.
* If any stop condition fires I stop after reporting 0a-0c (all three are always computed) and do not run the grid.

## 6. Guards (step 3), main-metric passes, harms
Common: same path = core voices + gain curves -> `render_multi`-style synthesis at 3 kHz for song metrics; for synthetic signals y48 = `R.up48(SY.render_layer16-style layer)` exactly as `plan16/D/guards.y48`.
* Main (B3): drum sum reduced >= 40 %; sum without T25 (core 0.0150) reduced >= 25 %; of the core-value >= 0.002 songs (T01, T05, T20, T25) >= 3 reduced by >= 30 %; core-value < 0.002 songs (T12, T40, T60) each <= core + 0.0005.  Also reported: T25 value and the no-T25 value, overall wrong_sa and non-drum wrong parts (information), no-bass songs: hit-linked share (information).
* Right layer F (M8: F only): pooled right-layer (comp 0 + 1) energy >= core - 0.5 dB; no BASS song worse than -1 dB (the 3 no-bass songs have ~no right layer and are excluded from this song-wise test, reported).
* Co-hit attack (M2): notes = all bass-MIDI notes (+tp pitches are irrelevant here, only start times) with start s_n inside the excerpt (0.5 s <= s_n <= dur - 0.1 s); co-hit if some d in H has |s_n - d| <= 30 ms, else "separate"; E(n) = sum of right-layer samples^2 (comp 0 + 1, F, 3 kHz after kOutSos) over [s_n, s_n + 60 ms].  Song ratio 10 log10(sum E_int / sum E_core) >= -2 dB (reset by 0c if needed), songs with < 8 co-hit notes excluded; fraction of notes with > 6 dB drop <= 20 % (pooled over the included songs; per song printed); notes whose core energy is below 1e-3 of the song median note energy are skipped (no meaningful ratio).  Also the same metric for notes overlapping a detector window (any overlap of [s_n, s_n+60 ms] with a window); separate-notes reported.
* Synthetic guards (B1 text): bare100/step25/bass9/bkp_0/steady8/logoff/gapbkp/t60 are run through the detector too (they should give 0 windows; the numbers are reported), and bkp-click variants (i) bass+click-kick, (ii) bass only without click, (iii) click-kick only.  Thresholds: V3i <= 0.5 /s; V4b <= core + 2 %p; gap/s <= core + 0.1; V5a <= core + 1 %p (6.19 %); V3d bass9 median <= 1 dB (line value reported only); RERISE median <= core; V7d (both hits) <= core; (ii) detections 0; (i) detections reported; rise90 (ii) <= core + 5 ms, rise90 (i) <= core + 30 ms (K1 20 ms + 10 ms ramp, per 16.10.1); (iii) ghost: layer energy in [t_d - 20 ms, t_d + 150 ms] around the detections <= core - 12 dB.
* bkp-click design (pre-registered, before any detection result): signal = `PX.sig_bass_kick_pink(0.0)` composition (bass + 0.2 kick + pink, 8 s, kicks at 0.5 n) for (i); (ii) = bass + pink (`X.bass_sig` + `X.pink_gf`, no kick, no click); (iii) = 0.2 kick + pink + clicks.  Click = 3 ms (144 samples) white noise, band-passed 2-6 kHz (4th-order Butterworth), added at every kick instant 0.5 n (n = 0..15, sample-aligned, not aligned to the 128-sample block grid); amplitude chosen so the burst energy in the 1-8 kHz band equals the pink floor's median 128-block 1-8 kHz energy x 10^(1.8) (+18 dB; +15 dB is the spec minimum, +3 dB margin for straddling a block boundary).  Detection ladder, fixed now: if variant (i) is detected on < 14 of the 15 kicks with t > 0.5 s the burst is raised to +21 dB, then +24 dB, and the first level reaching >= 14/15 is used; if +24 dB still fails the number is reported and the (i)/(iii) guards are reported as "detector does not fire on the pre-registered signal" (not silently passed).  The rise90 for the bkp signals is the per-onset form of the `v3h_bare` definition (5 ms box RMS of the 48 kHz layer, reference = mean over [t0+60, t0+110] ms as in `v3h_line` because the bass notes repeat every 0.5 s, so the 1.2-1.45 s reference of the single-note signal does not exist; first time >= 0.9 ref within 125 ms after t0), median over notes at 0.5 n, n = 2..14.
* M4 harms (per BASS song): note loss = number of bass-MIDI notes with length >= 200 ms whose right-layer energy in the last 2/3 of the note is more than 6 dB below the core's -> must be 0 (core vs itself is 0, so "<= core + 0" = 0); sustain pumping = for the part of the notes from s_n + 200 ms to e_n lying inside detector windows, right-layer energy (summed over the song) >= core - 1 dB (songs/windows with no overlap are reported as "no overlap").
* Leak (MINOR 4, M11 style): the detector's largest 48 kHz sample index read when the gain of an event first departs from 1 minus the sample index of that time (<= 128 samples = 2.7 ms by construction: the block that contains the trigger ends at most 128 samples after t_d, and the first gain knot is at the first alive window hop >= t_d); K1/K2/K3 logs the largest trace-hop/stream index read minus the index of the hop whose gain it changes (must be <= 0).  Criterion: detector lead <= 5 ms (240 samples); K reads <= 0.

## 7. Grid (registered before results)
3 axes, 12 settings (MINOR 1): detector threshold thr_db in {6, 9, 12} x initial gain in {-9, -12} dB x window W in {40, 60} ms.  Fixed: cap +3 dB, K1 30 cent / 16 ms, K2 30 cent and -20 dB, K3 120 dB/s, 2 consecutive hops, fades 5/10/15 ms, refractory 60 ms.  Literal setting (9, -12, 60) first.
Selection: among settings passing EVERY development condition (main, right layer, co-hit attack, synthetic guards, M4 harms, leak), the one with the largest drum-sum reduction; tie (within 1 %p of reduction) -> smaller right-layer loss.  None passes -> "no setting" (decision: stop, record failing items; confirmation tracks not processed).  The selected setting is frozen in `frozen_setting.json` BEFORE any confirmation track is processed.
